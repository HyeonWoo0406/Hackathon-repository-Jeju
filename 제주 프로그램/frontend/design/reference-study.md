# 프론트엔드 디자인 레퍼런스 연구

조사일: 2026-11-16

## 작업 전제

- 기존 크림색·초록색 디자인과 앞서 만든 후보는 채택하지 않는다.
- 작업 범위는 프론트엔드다. 기존 API와 제공 데이터 범위에서 설계한다.
- 색상만 다른 대시보드를 여러 후보로 제시하지 않는다.
- 실제 서비스의 제품 화면, 정보 구조, 조작 방식을 먼저 분석한다.
- 아래의 적용 의견은 조사자의 디자인 해석이며 해당 서비스의 공식 설계 의도를 뜻하지 않는다.

## 확인 범위

| 참고 서비스 | 실제 확인 자료 | 한계 |

| 캐시노트 | 공식 홈페이지의 장부·실적 캘린더 홍보 이미지 및 설명 | 이미지에 홍보 캐릭터가 겹쳐 있고 앱 전체 동작은 미확인 |

| Square | 공식 매출 요약·추이 보고서 사용 문서 | 인증된 최신 제품 화면과 세부 시각 스타일은 미확인 |
| Shopify | 공식 분석 개요·기간 비교 문서 | 인증된 관리자 화면을 직접 사용한 것은 아님 |

## 토스플레이스: 비교 문맥을 포함한 매출 보고서

출처:
- https://guide.tossplace.com/operate/sales-overview
- https://guide.tossplace.com/operate/sales-calendar
- https://tossplace.com/story/salesreport_detailed_analysis

관찰:
- 기간 선택과 이전/다음 이동이 결과 영역 위에 위치한다.
- 매출현황 이미지에서 비교 결과를 설명하는 짧은 문장 다음에 주요 수치와 그래프가 나온다.
- 밝은 중립 배경 위에서 파란색은 활성 항목과 주된 데이터에 집중된다.
- 현재 화면의 핵심 매출 수치와 취소·할인 같은 보조 수치의 시각적 비중이 다르다.
- 매출달력은 날짜·금액·날씨를 같은 날짜 칸에 배치하고 주간 합계를 별도 열로 보여준다.

적용 해석:
- 분석 주와 기준 4주를 화면 상단에서 함께 인지하게 한다.
- 요약 문장은 정해진 판정과 계산 결과만 표현하고 장식적 인사말보다 우선한다.
- 날짜 상세에 매출 변화, 동네 지표, 비·공휴일·비교 제외 사유를 모은다.
- 우리 데이터에는 주문 건수·객단가·결제수단 매출이 없으므로 해당 패널을 따라 만들지 않는다.
- 토스의 상품군 전체 메뉴를 복제하지 않는다. 현재 기능 수에 맞게 내비게이션을 줄인다.

## 캐시노트: 날짜를 기준으로 돌아보는 장부

출처:
- https://cashnote.kr/
- 공식 장부 이미지: https://bluebird-asset.cashnote.kr/uploads/image/image/43132/Frame_1171279307.png

관찰:
- 공개 장부 이미지에서 실적 캘린더가 중심적인 기능으로 제시된다.
- 매출·비용·주요 알림을 구분하는 선택 항목이 있고, 종류별 금액과 총액을 구별한다.
- 기능명이 사용자의 업무 언어로 짧게 제시된다.

적용 해석:
- 매출 입력과 결과 모두 날짜·요일을 안정적인 기준점으로 삼을 수 있다.
- 입력 없음, 실제 0원, 휴무, 자료 부족을 각각 다르게 표현한다.
- 최초 35일 입력에는 대상 주와 기준 4주의 구획 및 완료 상태를 보여준다.
- 해당 제품은 서비스 범위가 넓다. 금융·마켓·목표 설정·매출 순위는 우리 기능으로 추가하지 않는다.
- 홍보용 3D 캐릭터와 다색 금액 표시는 채택 근거로 삼지 않는다.

## Plausible: 한 화면의 수치와 그래프를 연결

출처:
- https://plausible.io/plausible.io
- https://plausible.io/

관찰:
- 공개 데모에서 지표를 각각 큰 장식 카드로 분리하지 않고 하나의 그래프 위 행에 정렬한다.
- 필터와 기간 선택은 공통 상단에 배치되어 전체 결과의 문맥을 유지한다.
- 큰 추이 그래프 아래에 출처·페이지별 목록이 이어진다.
- 기간 메뉴를 열면 사전 정의된 기간, 사용자 지정, 비교 기능을 한 메뉴에서 찾을 수 있다.
- 여백과 얇은 구분선을 주로 사용하고 그래프의 색을 제한한다.

적용 해석:
- 결산 화면을 거대한 제목과 여러 KPI 카드가 아니라 비교 자료를 읽는 작업 공간으로 구성한다.
- 우리 프로그램은 주간 비교가 정해져 있으므로 데모의 모든 기간 필터를 만들 필요는 없다.
- 요일별 변화율 비교를 중심 시각화로 두고, 한 요일을 선택해 상세 근거를 읽게 하는 구조를 검토한다.
- 매출 원 단위와 버스·와이파이 이용량을 같은 축에 직접 겹치지 않는다.
- 변화율로 비교하더라도 측정 대상이 다름을 명시한다. 동네 지표를 매출 또는 실제 방문자 수로 이름 붙이지 않는다.

## Square: 요약에서 상세로 가는 작업 순서

출처:
- https://squareup.com/help/us/en/article/5381-in-app-summaries-and-reports

공식 문서에서 확인한 점:
- 기간, 지표, 그룹화와 필터를 정해 매출 요약을 본다.
- 별도의 추이 보고서에서 두 기간을 비교한다.
- 보고서는 출력·내보내기 등의 후속 작업으로 이어진다.

적용 해석:
- '어느 주를 보는가 → 무엇이 달라졌는가 → 어느 요일을 확인하는가'의 순서를 유지한다.
- 현재 지원하는 인쇄/PDF는 결과를 확인한 뒤 사용하는 보조 행동으로 배치한다.
- 고급 필터를 처음부터 노출하거나 지원하지 않는 집계·다중 매장 기능을 만들지 않는다.

## Shopify: 비교 기준의 명시

출처:
- https://help.shopify.com/en/manual/reports-and-analytics/shopify-reports/overview-dashboard/using-the-overview-dashboard
- https://help.shopify.com/en/manual/reports-and-analytics/shopify-reports/report-types/custom-reports/time-ranges

공식 문서에서 확인한 점:
- 대상 기간과 비교 기간을 별도로 선택한다.
- 지표 요약에서 관련 상세 보고서로 이동한다.
- 기간 비교는 현재 데이터와 기준 데이터를 선의 실선/점선 또는 농도로 구별한다.

적용 해석:
- 감소율 옆에 비교 기준을 붙여 숫자만 남지 않게 한다.
- 같은 시계열의 기간 비교와 서로 다른 지표의 비교를 혼동하지 않는다.
- 가게/동네는 일관된 범례와 직접 표시를 사용하고, 기간을 구분하는 선 스타일을 무분별하게 섞지 않는다.
- 맞춤형 대시보드 편집 기능은 현재 범위에서 제외한다.

## 도출한 공통 설계 기준

1. 제목과 환영 문구보다 분석 주, 비교 기준, 자료 준비 상태를 우선한다.
2. 주요 수치는 화면 정렬로 구획하고, 모든 항목을 둥근 카드로 감싸지 않는다.
3. 색은 선택 상태, 시계열 구별, 오류 등 역할을 가져야 한다. 큰 장식 색면은 기본값으로 삼지 않는다.
4. 숫자의 자릿수·단위·부호·기준 기간을 같은 위치에서 읽을 수 있게 한다.
5. 수치 → 요일 → 근거가 연결되어야 한다. 사용자가 상세를 찾기 위해 같은 정보를 다시 탐색하지 않게 한다.
6. 로딩, 수집 대기, 자료 부족, 실제 0원, 휴무는 각각 구분한다.
7. 질문 기능은 현재 결산의 근거를 읽는 보조 수단으로 둔다. 일반 상담·전망·원인 진단처럼 보이게 하지 않는다.
8. 최초 설정과 반복 사용 화면은 구별한다. 매주 쓰는 사람에게 가게 등록을 다시 강조하지 않는다.
9. 지역성은 주소·정류소·날씨 등 실제 정보로 표현한다. 제주 관광 일러스트를 장식 목적으로 넣는 것부터 시작하지 않는다.
10. 다음 시안은 같은 실데이터 구조를 사용하되, 달력 중심 / 비교 그래프 중심 / 한 장 결산서 중심 등 사용 구조부터 다르게 설계한다.

## 다음 시안 비교 기준

- 분석 대상 주와 비교 기준을 즉시 찾을 수 있는가?
- 가게 매출과 동네 지표의 관계 및 한계를 오해하지 않는가?
- 특정 요일의 근거에 적은 조작으로 도달하는가?
- 처음 35일을 준비하는 부담을 줄이는가?
- 좁은 화면에서도 핵심 숫자와 행동이 읽히는가?
- 기능 수에 비해 화면이 과장되거나 복잡하지 않은가?

조사 과정에서 프론트엔드 구현과 백엔드 코드는 변경하지 않았다.
